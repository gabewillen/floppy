# `builder` implementation report plan

The implementation report plan of [`builder.scx`](../builder.scx): the W3C SCXML IRP's
manifest format and `Outcome` oracle over the document's numbered
statements below, one assertion each in [`manifest.xml`](manifest.xml),
tested by the harness documents in [`sources/`](sources). Each harness
invokes the document as its child, drives it, and ends in `pass` (logging
`Outcome` `pass`) or `fail`. `tests/tests/document_irp.rs` runs every case
through `scx run` with the real invoked services (a case's
`backend.json` scripts the fake HTTP backend they reach), and
`tests/irp/harness.py` writes the cases from [`cases.py`](cases.py).

## Statements

- <a id="builder-1"></a>**builder-1**. It waits in `intake` for `builder.request` `{spec, name?, constraints?, context?, max_attempts?, model?, generate_timeout_ms?, generate_ceiling_ms?, min_every_ms?, turn_after_bound_ms?, apply?, document_max_completion_tokens?}`; data its schema refuses is refused at the sender (its send raises `error.execution` there) and the builder keeps waiting; a request whose spec is only whitespace ends in the final state `failed` with `{reason: "invalid-request", diagnostics: [{kind: "request", code: "invalid-request"}]}`, which the invoker receives as `done.invoke.<id>`.
- <a id="builder-2"></a>**builder-2**. A request is planned (`design`, schema `topology_plan`), authored (`author`, schema `scxml_draft`: its `scxml`, `schemas` and `script`), written as `<name>.scx`, `<name>.json` and `<name>.js` through the files service (`writing`; the request's `name`, else the plan's; decision D121), validated (`validate`) and simulated (`simulate`, each test script driving the draft as an invoked child by `srcexpr` on its path); a draft that validates and passes every test ends in the final state `done` with `{scxml, schemas, script, path, tests, report: {attempts, failures, fixes_applied, warnings, plan, decisions, history, simulation}}`, `path` `../../behaviors/<name>.scx`.
- <a id="builder-3"></a>**builder-3**. A draft whose validator errors all have machine-applicable fixes is fixed (`apply_fixes`, at most 2 passes per draft) and validated again, without a new attempt: `report.fixes_applied` counts it.
- <a id="builder-4"></a>**builder-4**. Every failure goes through `retry_gate`, then `triage`, which asks the decision service to choose among its enabled transitions: `triage.repair` authors the draft again from the same plan (`report.decisions` `["triage.repair"]`), `triage.redesign` plans again, `triage.abandon` ends in `failed` `{reason: "abandoned"}`. When the decision is unavailable it falls back (`fallback`): repair when there is a plan, else redesign.
- <a id="builder-5"></a>**builder-5**. A failure with a diagnostic an earlier failure of the build had does not end the build (decision D133); at `max_attempts` failures, 8 unless the request sets it, it ends in `failed` `{reason: "attempts-exhausted"}` with the last diagnostics and, when a check rejected a draft, its `scxml`.
- <a id="builder-6"></a>**builder-6**. Each check has its own diagnostics: a validator error (`kind` `validate`, its code), a draft that cannot be written (`draft` `write-failed`), test scripts out of bounds (`draft` `tests-out-of-bounds`, one to eight), and a test whose outputs or done differ from its expectations (`simulate` `test-failed`).
- <a id="builder-7"></a>**builder-7**. A generation that fails (`generate.failed`) is a `generate` diagnostic `<stage>-failed`; one that runs `generate_ceiling_ms` in all, or, once its reply streams, makes no progress for `generate_timeout_ms` (the first `generate.progress` arms it, each later one re-arms it), is cancelled, a `timeout` diagnostic `<stage>-timeout` (decision D101).
- <a id="builder-8"></a>**builder-8**. With the request's lifetime bounds (`min_every_ms`, `turn_after_bound_ms`), a draft that sends `bot.behavior.tick` (a persistent routine) whose schedule is shorter than `min_every_ms` is a `lifetime` diagnostic `E0009`; a routine within the bounds also gets a forced first tick, whose output must select at least one event (else an `apply` diagnostic `E0008`).
- <a id="builder-9"></a>**builder-9**. With the request's `apply` `{turn, input, targets, choices?, handled?}`, a draft that sends no `bot.behavior.tick` also runs once with the params `turn` and `input` (the simulation result `live turn`) and must end within min(`turn_after_bound_ms`, 2000) ms in a top-level final state whose donedata is `{turn, handled: true, selected}` (or, with `handled` false, a turn that taught the behavior, `handled` false) with the live turn and selections naming targets among `targets` with data agreeing with `input` and, with `choices`, each an event its target takes with data its schema admits, else an `apply` diagnostic `E0008` (`<behavior:verify_apply>`, decisions D131, D221 and D222).

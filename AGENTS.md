# Project rules

These rules are normative for every contributor to this repository, whether a
human or an AI coding agent. [CONTRIBUTING.md](CONTRIBUTING.md) describes the
workflow and proof commands; [.agents/rules/project.rules.md](.agents/rules/project.rules.md)
restates the conformance rules. MUST, SHOULD, and MAY are used as in RFC 2119.

- Contributors MUST treat this repository as a WebAssembly Component Model-first SCXML product; native Rust builds MAY support tests, tooling, and hosts but MUST NOT become the deployment semantics.
- The deployable machine MUST be the one generic `scxml-machine` component containing the deterministic `scxml-engine`, which MUST execute inside that component; it MUST embed no machine-specific tables or generated code and MUST receive lowered Machine IR only as immutable, version-checked data through the `stateforward:scxml/ir-source` import, served either by the host at run time or by a data-only provider component composed in for a packaged `ComponentWasm`.
- Native and browser hosts MUST remain thin capability linkers and lifecycle adapters, and MUST NOT parse SCXML, select transitions, implement macrosteps or microsteps, evaluate conformance outcomes, or duplicate engine semantics.
- Conformance runners MUST compile through the canonical compiler and execute through `scxml-engine`; they MUST NOT implement a second transition selector or substitute final-state guesses for engine behavior.
- Validators, compilers, data models, I/O processors, invoked services, executable content extensions, rustc-style reporters, and SARIF reporters MUST be independently deployable Wasm components behind versioned WIT contracts.
- SCXML/XML, XSD, extension package manifests, snapshots, configuration, prepared conformance corpora, and lowered IR MUST remain declarative data and MUST NOT silently substitute for executable components.
- New component crates, worlds, and artifacts MUST use concise domain names and MUST NOT add a redundant `-component` suffix.
- The exact canonical SCXML namespace URI MUST be `http://www.w3.org/2005/07/scxml`; namespace lookup MUST use the exact expanded URI and MUST NOT rewrite prefixes, case, spelling, or trailing slashes.
- Extension package manifests MUST bind the exact namespace URI, package version, extension component Wasm artifact, schema artifact and SHA-256 digest, WIT world, and WIT version, and MUST declare the outbound HTTP origins (`http-origins`, the component's whole outbound allowlist: binding or loading the package consents to it) and the `env` slots (`env-slots`) its elements accept; invoked-service package manifests MUST declare the same two lists. Manifests declare `http-origins` and `env-slots` only: no WASI and no events. Unknown fields (the removed `wasi-permissions` and `events` included) MUST fail closed when the manifest is read.
- A repository namespace (a namespace URI of exactly `https://github.com/<owner>/<repo>/namespaces/<name>[@<tag>]`; `@<tag>` pins that release, and a tagless URI names the repository's latest GitHub release; the built-in tagless vocabularies `scx` provides, `env`, `event`, and `scx`, MUST be matched first and MUST never be fetched) MAY be acquired only by the CLI's bounded resolver, only for a namespace the document (or an `<invoke src>` document the run loads) uses that no flag binds, only when `validate`/`compile` read its document (manifest and schema) or `snapshot run`/`run` bind it before the session starts (the component): the tag (or the latest release's `tag_name`) resolved to a commit, manifest and schema fetched at that commit and verified (exact URI, schema SHA-256, `targetNamespace`, WIT identity; the manifest names the exact URI the document binds, tagless or pinned), the component verified against the release's `SHA256SUMS`, HTTPS only (loopback HTTP only for explicit test or mirror bases), redirects only to GitHub or configured origins and bounded, explicit timeouts, no retry, bounded bodies, no ambient credentials. Acquired bytes MUST be cached exactly, content-addressed, with the URI pinned to its resolution's commit and digests (a tagless URI also records its release tag); a pinned URI's later runs MUST re-verify and use no network, a tagless URI asks for the latest release once per root session and re-pins only when it names another commit, `--offline` MUST forbid every fetch (a tagless URI then uses its pinned release), and any failure MUST fail closed (validation stops, or the run fails before the first macrostep). Each URI MUST be resolved once per root session, and every invoked session (inline `<content>` or `<invoke src>`) MUST share the root's resolved, compiled component for the same URI (one instance per session); a pinned and a tagless URI of one package are distinct and MAY coexist. The host and engine MUST NOT acquire anything themselves. A repository service (an invoked-service type URI of exactly `https://github.com/<owner>/<repo>/services/<name>[@<tag>]`, never a repository namespace) follows exactly the same rules, acquired only by the CLI's bounded resolver for a literal `<invoke type>` the document or a loaded `<invoke src>` document names that no `--service-package` binds: its manifest (exact `service-uri`, WIT identity) and optional schema fetched at the release's commit and verified against the digests the manifest declares, and its component verified against the release's `SHA256SUMS` when `snapshot run` or `run` binds it, before the session starts; the same cache, pinning, `--offline`, sharing, and fail-closed rules apply, and the embedder binds the verified component (`ServiceComponents`).
- `snapshot run` and `run` MUST load `<invoke src>`, `<script src>`, and `<data src>` by SCXML's defaults: `https:`, `file:`, and relative URIs (resolved against the base URI of the document that names them). Every literal URI of the document and of every `<invoke src>` document it loads MUST be fetched once, before the first macrostep, through the same bounded fetcher (HTTPS only for remote documents, bounded size, redirects, and time, no retry, no credentials, nothing under `--offline`), and listed in the consent output; a `<script src>` of the document that cannot be fetched MUST reject the document (SCXML 5.8), and any other failure raises `error.execution` when its element runs. An `<invoke srcexpr>` URI is fetched when the `<invoke>` runs, through the same fetcher, and a failure raises `error.execution`. Everything is fetched once per root session and shared by every session of the tree.
- An invoked-service component's WASI interfaces MUST be exactly its own `wasi:*` imports; nothing WASI is ambient and no manifest declares WASI. Only runtime resources MAY be granted, named with wasmtime CLI's options and scoped to the service's exact type URI (`--dir URI=HOST::GUEST` for `wasi:filesystem`, `--wasi URI=inherit-network` for `wasi:sockets/tcp`, `--wasi URI=allow-ip-name-lookup` for `wasi:sockets/ip-name-lookup`; `ServiceComponents::with_wasi`). A host MUST fail closed when the service is bound, before anything runs, for an import without its grant, a grant without its import, or a `wasi:*` import it never links (`wasi:cli`, `wasi:http`), and MUST keep the WASI host stack inside the host adapter; the CLI MUST list each service's WASI imports and the resources the run grants it before running. Executable-content extension elements run inside a microstep, so they MUST stay synchronous and quick; anything asynchronous, I/O-bound, or long-running belongs in an invoked service (SCXML 6.4). By that rule (not as a gap), extension components MUST get no WASI interface, and a host MUST link WASI interfaces only into invoked services. An invoked service's `outbound-http.fetch` is a Component Model `async func` that MUST suspend only the calling task, never the session; its responses are recorded inputs, so `--record` and `--replay` MUST work with services. An extension component's `fetch` blocks its synchronous `execute` and is for quick requests.
- Extension components MUST NOT receive secret values: an element names variables for its declared slots with the host's `env` attribute vocabulary (`https://github.com/stateforward/scxml.rs/namespaces/env`), the host passes opaque per-execution, per-element references, and substitutes values only into that element's `outbound-http` requests admitted to a declared origin or an origin a value supplies entirely; every other request MUST be refused before it is sent. The CLI MUST mask the run's values in the text it writes (canonical snapshot documents, whose digests cover their bytes, are written exactly and get canonical-artifact protections), and MUST list, before running, each element's namespace, version, declared origins, and the slots the document binds (never a value). Invoked-service components MUST NOT receive secret values either: an invoked service's `<invoke>` names variables for its package's declared slots the same way, and the host passes opaque references (`invoke-request.references`) bound once per invocation that stay valid for that invocation's lifetime (not per call) and substitutes values only into that invocation's admitted `outbound-http` requests.
- Extension-namespace XSD MUST govern XML structure and datatypes, while the linked Wasm extension component MUST govern executable behavior; schemas MUST NOT execute behavior, and validator/compiler schema checks MUST NOT require behavior instantiation.
- Unknown, missing, mismatched, or digest-invalid extension packages MUST fail closed according to the explicit schema policy and MUST NOT degrade silently into core SCXML semantics.
- XSD validation MUST validate the structure of SCXML or transformed XML; XSLT MUST be confined to explicit W3C IRP corpus specialization and MUST NOT be used as product validation or runtime semantics.
- The compiler MUST NOT invoke `rustc` or another native compiler from Wasm; packaging SHOULD use pinned prebuilt templates and deterministic encoder/component tooling.
- `LoweredIr`, `CoreWasm`, and `ComponentWasm` MUST remain distinct, truthful artifact phases.
- `LoweredIr` bytes MUST be described as deterministic portable machine data and MUST NOT be described as WebAssembly.
- `CoreWasm` bytes MUST be described as a core WebAssembly module and MUST NOT be described as a Component Model component.
- `ComponentWasm` MUST be claimed only after final component bytes are emitted, validated, and exercised through the required runtime proof.
- Validator, compiler, and IRP producers MUST emit canonical versioned output as the sole source of truth for downstream reporters.
- Reporter components MUST consume canonical producer bytes, MUST reject unknown versions, kinds, and fields, and MUST NOT rerun validation, compilation, conformance execution, or decision logic.
- Canonical outputs MUST encode deterministic field order, sorted unordered collections, stable identifiers and counts, explicit versions and kinds, and enough provenance to detect drift or tampering.
- Canonical outputs and snapshots MUST be byte-deterministic for identical accepted inputs, configuration, toolchain, and runtime environment.
- Canonical validator artifacts MUST preserve exact source spans and MAY preserve source names and complete source text for independent rendering; such artifacts MUST receive the source document's access, retention, transport, and redaction protections.
- Secrets, credentials, source payloads, expressions, personal data, proprietary content, and canonical report bytes MUST NOT enter logs or indexed telemetry.
- The validator MUST remain the primary AI authoring interface and MUST return bounded, deterministic, actionable diagnostics rather than prose-only failures.
- Validator semantic quality MUST meet or exceed the documented AgentML rule inventory baseline without copying AgentML architecture, and remaining gaps MUST be stated explicitly.
- Diagnostics MUST provide stable codes, severity and category, exact UTF-8 byte spans, primary labels, related spans and labels, actionable help, specification references, and rustc/clippy-style fixes with explicit applicability when a repair is honest.
- Diagnostic and fix decoders MUST reject invalid UTF-8 boundaries, out-of-range spans, overlapping edits, inconsistent counts, and unsupported schema versions or kinds.
- Untrusted XML, XSD, package manifests, canonical report bytes, Wasm inputs, snapshots, IR, and all other serialized data MUST be structurally validated, semantically validated, and version-checked before core use, and bounded as the bound rule below requires.
- Unknown fields, versions, enum values, artifact kinds, capability kinds, and semantic constructs MUST fail closed rather than be ignored.
- Expected failures MUST use typed `Result` or domain error contracts with preserved safe context and MUST fail closed at trust boundaries.
- Production code MUST NOT use unhandled `unwrap()`, `expect()`, `panic!()`, `todo!()`, `unreachable!()`, indexing known to panic, unchecked conversions, or ignored `Result` or `Option` values on reachable input or runtime paths.
- Tests MAY use `unwrap()` or `expect()` only when the failure message makes the tested invariant clear.
- Const, build-time, or otherwise provably infallible cases SHOULD still use explicit handling; any panicking API retained there MUST have an immediate local justification proving the invariant.
- Integer and size conversions MUST be checked, bounded, and mapped to typed failures or explicitly documented saturation; truncating or unchecked conversions MUST NOT cross trust boundaries.
- Workspace and authored crates MUST use `#![forbid(unsafe_code)]` wherever target or generated-binding constraints permit.
- Authored unsafe code MUST NOT be added without explicit maintainer approval for the exact scope, a documented soundness contract, minimal unsafe blocks, tests, fuzzing or equivalent evidence, and a removal or containment plan.
- Dependency and generated-binding unsafe code MUST be isolated, pinned, and audited, and MUST NOT be treated as permission for authored unsafe code.
- Public contracts MUST define caller preconditions, provider postconditions, stable invariants, ownership and aliasing, side effects, failure categories and effects, bounds, versioning, and trust-boundary validation close to the governed code.
- Contract checks MUST be deterministic, bounded, side-effect-free, and tested for accepted inputs, rejected inputs, boundaries, expected failures, and representative success paths.
- Parsers, decoders, serializers, validators, state machines, and unsafe dependency boundaries SHOULD have property, hostile-input, fuzz, or equivalent generative tests.
- Resource bounds (sizes, counts, queue lengths, payload sizes, command counts, fuel, and the loop iterations a document programs) MUST apply to wasm builds only, declared through `scxml_types::wasm_bound`; a native build MUST NOT reject a document or end or fail a session because of a bound it imposes itself. On every build, native stack guards (parser, walker, and recursion depth), work and amplification guards (work or output that grows faster than its input), format and interface bounds (WIT, snapshot, wire, and Machine IR widths), network-ingress protections, and artifact authentication MUST bound what they guard, and retries and waits MUST have explicit upper bounds.
- Core logic MUST receive clocks, randomness, filesystems, networks, environment, storage, and external services through explicit capability boundaries and MUST NOT read ambient mutable state.
- Mutable resources, tasks, subscriptions, handles, and shared state MUST have one clear owner or a documented synchronization and cancellation contract.
- Cargo metadata MUST be authoritative for package names, versions, edition, Rust version, features, dependencies, license, repository, and publication metadata.
- The workspace MUST remain on Rust `1.98`, edition `2024`, and Cargo resolver `3` unless an explicit reviewed migration changes all authoritative metadata and proof together.
- `Cargo.lock` MUST remain committed for reproducible workspace, CLI, host, and component builds.
- Dependencies and features MUST remain minimal, additive, pinned or constrained reproducibly, and default features SHOULD be disabled unless required and justified.
- `cargo audit`, `cargo deny`, or an equivalent dependency and license policy check SHOULD gate security-sensitive changes, and accepted advisories or exceptions MUST name an owner, rationale, evidence, expiry, and removal plan.
- Heavy or platform-specific dependencies MUST stay behind compile-time-optimized crate boundaries: `quick-xml` MUST remain inside syntax parsing, `xsd-schema` MUST remain inside the XSD adapter, Wasmtime MUST remain inside the host adapter, and guests/core crates MUST NOT inherit host-only stacks.
- Domain, syntax, validation, lowering, engine, reporting, telemetry, WIT, component-adapter, and host concerns SHOULD remain separate crates so unrelated changes do not force broad feature coupling or compilation.
- Pre-1.0, undeployed replacements and renames MUST use hard cutovers that remove the old path, tests, configuration, documentation, aliases, fallbacks, and unused files in the same change.
- Compatibility shims, deprecated aliases, legacy fallbacks, version-suffixed duplicates, and migration flags MUST NOT be added unless a named released or deployed consumer requires them and a retirement condition is documented.
- Production code MUST emit OpenTelemetry through the `scxml-telemetry` facade (or the versioned WIT telemetry facade in guests, or the OpenTelemetry JS API in the browser host) at boundaries: component and WIT entry points; the public operations of the facade crates (validate, compile, package, run one host call, engine command, or effect transaction, snapshot); capability and I/O calls; host lifecycle (load, link, instantiate, session start and shutdown); and the failure paths of those boundaries.
- Getters, accessors, conversions, formatting, pure predicates, private helpers, and hot inner loops (transition selection, configuration and hierarchy queries, per-token or per-byte scanning, codec internals) MUST NOT emit spans or events of their own; the enclosing boundary span covers their work, and their failures surface as the boundary's typed failure.
- Every span and operation name MUST describe exactly the operation it covers; one operation label MUST NOT be reused for an unrelated operation, and labels that no longer cover an operation MUST be removed in the same change.
- Telemetry MUST NOT measurably regress hot paths; any claim that instrumentation is cheap, or that a change improves or preserves performance, MUST cite benchmark evidence (`cargo run --release --locked -p scxml-bench`) or a profile.
- Wasm guests MUST use the versioned telemetry WIT facade and MUST NOT embed an OTEL SDK or exporter; native hosts MUST own SDK, provider, and exporter installation.
- Every OTEL metric dimension, span attribute, resource attribute, log attribute, and event label MUST have a documented bounded-cardinality analysis before completion.
- Test IDs, paths, URLs, namespace URIs, component identities, event or state names, expressions, payloads, messages, digests, source text, timestamps, and other unbounded values MUST NOT be indexed telemetry attributes.
- Fuel, command counts, effect counts, and similar quantities MUST be numeric measurements rather than indexed labels, and telemetry MUST NOT alter deterministic behavior or output.
- The official W3C SCXML IRP manifest and `.txml` corpus MUST be the conformance source of truth and implementation oracle.
- Synthetic and bespoke fixtures MAY test parser, runner, filtering, snapshot, denominator, tamper, and exit behavior, but MUST NOT be labeled as official passes or used for completion claims.
- Corpus acquisition and XSLT transformation MUST occur only through an explicit preparation command; ordinary tests and conformance runs MUST NOT use implicit network access or invoke XSLT.
- Offline preparation MUST consume pinned local bytes; intentional online preparation MUST be explicit and MUST cache exact acquired bytes.
- Prepared artifacts MUST record manifest source, revision, manifest digest, acquired source-set digest, data model, template digests, transformer command and version identity, per-case source/output/dependency digests, and preparation failures.
- Upstream IRP corpus and template licensing and provenance MUST be verified before vendoring or publication; byte identity MUST NOT be treated as a license grant.
- The official pass oracle MUST be exactly one executable log record whose label is `Outcome` and whose evaluated value is exactly `pass`, in a root session that finished in exactly the `pass` final state the W3C templates generate for `conf:pass`; `fail`, missing, invalid, or multiple Outcome records, and a pass record in a session that kept running or finished elsewhere, MUST NOT pass. The only exception is the documented manual-equivalent oracle for the W3C manual cases listed below.
- Applicable Selected IRP MUST include every selected non-filtered case, including cases the W3C manifest marks as manual, even when the implementation cannot execute it; manual cases MUST always run through the same pipeline and MUST NOT be skipped or excluded by default. The only exception is a case the W3C itself declares not applicable to the prepared data model, or whose W3C assertion and upstream test document fix a different data model so that the prepared specialization never exercises its own: it MUST be declared with quoted W3C evidence in the checked-in, digest-bound errata file bound into the prepared corpus and report identities, reported as `NotApplicable`, and never counted as passing.
- An official case whose upstream W3C template or `.txml` source is defective MAY be corrected only by a checked-in erratum that cites exact line evidence, corrects the test input (never how the implementation is judged), and binds the SHA-256 of both the upstream-produced and the corrected output; preparation MUST fail closed on either digest drifting, the corrected case MUST still be decided by its real oracle, and every pass under an erratum MUST be reported and counted as such.
- `Not Passing` MUST equal `Failed + Unsupported + Invalid + HarnessError`; `Unsupported` MUST remain an actionable temporary implementation gap and MUST NOT count as passing.
- The W3C manual IRP cases 178, 230, 250, 301, 307, and 415 cannot emit an `Outcome` of `pass`; they are official W3C cases (never synthetic fixtures) decided by the documented manual-equivalent oracle in `crates/scxml-conformance/src/manual_oracle.rs` (and optional manual case 513 by the manual-equivalent oracle the external-client harness implements in `crates/scxml-conformance/src/external_client.rs`), which MUST check exactly what the quoted W3C manual instruction asks a human to verify, over the session-attributed execution trace of the real engine run. That oracle MUST apply only to those official manual cases, MUST NOT change the `Outcome` oracle for any other case, MUST record `oracle: manual-equivalent` on every case it decides, and MUST bind its name, table version, and source digest into the report identity; any change to a checked condition MUST bump its version. Each such case stays Not Passing until its real run satisfies that oracle, and MUST NOT be skipped, reclassified, or hidden to reach completion.
- Every conformance case whose execution reached oracle evaluation MUST record the oracle kind that decided it (`outcome-log`, `manual-equivalent`, or `synthetic-expectation`); reports whose oracle kind contradicts the disposition, corpus provenance, or manual-equivalent table MUST be rejected.
- Mandatory completion MUST mean every applicable selected official mandatory case is `Passed` for one exact recorded corpus, template, transformer, data-model, runner, IR, filter, and artifact identity.
- Development overrides such as `--allow-not-passing` MAY change process exit only and MUST NOT remove, hide, or reclassify conformance gaps.
- Baseline comparison MUST reject incompatible identities by default, and regressions MUST be exactly prior `Passed` to current non-`Passed` transitions.
- Missing compiler, engine, data-model, namespace, executable-content, hierarchy, history, parallel, event, invoke, or oracle capabilities MUST produce explicit fail-closed dispositions with stage and bounded reason codes.
- Parsers, compilers, runners, hosts, and adapters MUST NOT silently drop conditions, eventless transitions, hierarchy, multi-target semantics, executable content, sends, invokes, extension namespaces, events, payloads, or unknown constructs.
- Native, Wasm, WIT, and Wasmtime proof MUST cover `cargo fmt --all --check`, workspace check/test/clippy with warnings denied, all executable guest builds for `wasm32-wasip2`, `wasm-tools validate`, WIT package resolution, Wasm checks for portable adapters, and Wasmtime host feature checks/tests.
- Generated `ComponentWasm` readiness MUST additionally prove instantiation and representative execution under Wasmtime against canonical WIT and MUST prove that packaged and runtime IR modes behave identically and match pinned expected traces, without claiming equivalence from compilation alone.
- Current status MUST state honestly which lowering, engine, data-model, packaging, and host capabilities are implemented and which remain gaps, with exact evidence: the checked-in IRP baselines with their run identity and digests, and the named tests and proof scripts that exercise each capability. It MUST NOT claim complete macrostep/microstep, scheduling, durable persistence, data-model expression, executable-content, I/O processor, or invoked-service semantics beyond that evidence.
- Current status MUST claim `ComponentWasm` packaging, generated-component execution under Wasmtime, browser execution, and component data-model execution only to the extent current proof demonstrates, and MUST NOT present parity proven for specific machines and event sequences as general equivalence.
- Current status MUST state which schemas, data-model templates, and corpora are bundled with license and digest provenance and which are not; official counts MAY be claimed only from an exact prepared run identity.
- Current status MUST state honestly which executable content is lowered and executed by the engine; data-model expressions flow through the data-model adapter to the exact Outcome oracle, while unsupported data models and executable-content semantics remain `Unsupported` rather than passing by final-state inference.
- The current-gaps list in `docs/limitations.md`, and its summary in the README's "Current limitations" section, MUST be kept accurate in the same change that closes or opens a gap. At the time of writing it includes: no send type other than the SCXML and BasicHTTP Event I/O processors (any other type raises `error.execution`); XPath IRP cases 241, 244, 307, 520, and 534 pass only under the documented upstream errata in `tests/conformance/w3c-irp/errata/xpath.json`, and 24 XPath cases that never exercise the XPath data model are `NotApplicable` to it per the W3C (301-304 scripting only; 436 fixes `datamodel="null"`; the 19 B.2 ECMAScript-profile cases fix `datamodel="ecmascript"`), and ECMAScript case 436 is `NotApplicable` to the ECMAScript corpus for the same reason (`tests/conformance/w3c-irp/errata/ecmascript.json`); the IRP results are measured through the shipped components under the Wasmtime session host, the only conformance execution path; Boa 0.22 has no allocation hook or interrupt, so ECMAScript evaluation is bounded structurally (with Wasm memory and fuel, or only process limits natively, as the outer bound); no durable cross-process persistence; the compiler component's packaging path is not exercised under Wasmtime; the proof hosts answer `raise`, `send`, `cancel`, and extension-namespace capability calls with `unavailable` (the machine's own `<raise>` is engine-internal); and the browser host loads URLs only through the page (its allowlisted `resources` option or `loadDocument`; a runtime `srcexpr` URL through `resources` only in a cross-origin-isolated `async: 'auto'` worker session), and async sessions do not take the `http` option.
- Documentation, tests, examples, WIT, schemas, and generated artifacts MUST stay synchronized with their canonical contracts, and CI SHOULD fail on detected drift.
- Changes MUST be narrowly scoped, deterministic, reproducible, and supported by tests and artifacts matching the exact claim; performance claims MUST include benchmark, profile, or production telemetry evidence.
- Contributors MUST run the smallest relevant proof during iteration and MUST run the full affected native/Wasm/WIT/Wasmtime matrix before claiming completion for those surfaces.
- AI agents MUST NOT create commits, amend commits, push, open pull requests, or merge unless the maintainer directing the work explicitly requests the exact action.
